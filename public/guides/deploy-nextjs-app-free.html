How to deploy a Next.js app with server-side rendering

JavaScript · Next.js6 min readUpdated 21 November 2026

A Next.js app is more than a folder of static files. Server components, route handlers and server-side rendering need a running Node.js process. Shipzo builds your app with next build and runs it with next start inside a container, so whatever works with npm run build && npm start on your machine works online too.

Quick answer
  1. Check that npm run build succeeds locally.
  2. Commit your lock file (package-lock.json, yarn.lock or pnpm-lock.yaml).
  3. Add NEXT_PUBLIC_ variables before deploying; keep secrets in variables without that prefix.
  4. Use the Standard plan or higher, because a Next.js server needs more memory than a static site.

How Shipzo runs Next.js

When next appears in package.json, Shipzo uses a Node 20 image, installs dependencies with npm ci (falling back to npm install), runs npm run build and starts the server with next start -p $PORT -H 0.0.0.0. There is nothing to configure.

Step 1: Make sure it builds

npm install
npm run build
npm start        # open http://localhost:3000

If the build fails on your computer, it will fail on the server too. Type errors and lint errors stop next build by default, so fix them first.

Step 2: Environment variables

Next.js has two kinds of variables, and mixing them up causes most deployment bugs:

  • Public variables start with NEXT_PUBLIC_. They are copied into the JavaScript sent to browsers when the app is built. Shipzo writes them into the build for you, but changing one only takes effect after a redeploy.
  • Server-only variables, such as DATABASE_URL or an API key, have no prefix. Read them with process.env in server components and route handlers. They never reach the browser.

Add both kinds under Settings → Environment variables. Never give a secret the NEXT_PUBLIC_ prefix, because anyone can read it in the page source.

Step 3: Pick a plan

A Next.js server keeps your pages, its caches and its image optimizer in memory. The free Starter plan (256 MB) is tight for that, so choose Standard (512 MB) or Pro (1 GB). If the dashboard shows the container restarting, it is usually running out of memory. Setting images: { unoptimized: true } in next.config.js also lowers memory use on small plans.

What about static export?

If your config has output: 'export', the app is fully static and next start refuses to run it. Either remove that line, so the app runs as a server, or add your own Dockerfile that serves the out/ folder with a static web server.

Step 4: Push and deploy

git add .
git commit -m "Ready to deploy"
git push

Open New deployment, paste the repository link, pick a plan and press Deploy. Your app is live at https://your-app.shipzo.tech, and later pushes redeploy it with zero downtime.

Common errors and fixes

ProblemFix
Type error: ... during the buildFix the error locally; the build log shows the file and line.
Container keeps restartingOut of memory. Move to Standard or Pro.
A NEXT_PUBLIC_ value is undefinedAdd the variable, then redeploy so it is built in.
"next start" does not work with "output: export"Remove output: 'export', or add a Dockerfile for the static files.
API route returns 404Check the file path, for example app/api/hello/route.ts.

Frequently asked questions

Does the App Router work?

Yes. The app runs with next start, so the App Router, server components and route handlers all work.

Do ISR and revalidate work?

Yes, within one running server. The cache starts empty after each deploy, because every release begins with a fresh container.

Can I use a separate backend with Next.js?

Yes. Deploy the backend as its own Shipzo project and put its address in a NEXT_PUBLIC_ variable.
